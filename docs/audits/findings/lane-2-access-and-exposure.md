## Findings

### F-2-7: The product cannot tell "you are not signed in" from "we could not reach the sign-in service", and it always guesses the first

- **file:line** — src/lib/auth/current-user.ts:14-18 (the read side), with the same
  pattern at src/app/actions/create-group.ts:66-76 and
  src/app/actions/join-group.ts:34-48 (the write side)
- **consequence** — Every screen in the product decides who you are by asking Supabase's
  sign-in service. That question can come back three ways: yes, no, and "I could not
  reach the service." The code reads the third answer as the second, everywhere, with no
  exception. Two things follow, and the second is the expensive one.
  On the **reading** side, if Supabase's auth service has even a brief wobble while
  someone is using the app, a real member is treated as a stranger: their own group home,
  their event pages and the group info page all replace themselves with "This group is
  invite-only. If you know someone in it, ask them for the invite link." To the person
  holding the phone that reads as "I have been removed from the group," not as "something
  is temporarily broken." This is the screen the investor would be looking at.
  On the **writing** side it is worse. Group creation and joining both work by asking
  "do you already have an account?" and creating a fresh anonymous one only if the answer
  is no. An unreachable service answers "no." So a founder who already has a group, hits
  a wobble, and taps through onboarding gets a brand-new blank identity and a brand-new
  group; from that browser their original group is now gone, because the front door sends
  people to the groups their *current* identity belongs to, and this new one belongs to
  none. Unless they had saved their own invite link, there is no way back in until email
  sign-in exists. The project's own build notes describe this session check as "the
  primary guard" against duplicate accounts; it fails open, silently, exactly when the
  service it depends on is unwell.
  Worth naming the contrast: the product goes to real trouble to classify *model* failures
  honestly, telling the difference between "out of credits" and "the service is having
  trouble" and saying which. The service that gates every single screen gets none of that
  care.
- **evidence** — `src/lib/auth/current-user.ts:12-18`:
  ```
  const supabase = await createClient()
  const {
    data: { user },
  } = await supabase.auth.getUser()

  if (!user) return null
  ```
  The `error` field of the response is not destructured at any call site. I checked all
  eleven: `current-user.ts:14-18`, `create-group.ts:66-68`, `join-group.ts:34-36`,
  `rsvp.ts:47-49`, `gauge-vote.ts:56-58`, `proposal-vote.ts:54-56`,
  `proposal-answer.ts:45-47`, `send-message.ts:60-62`, `leave-group.ts:35-37`,
  `remove-member.ts:30-32`, `reset-invite-link.ts:28-30`. Every one destructures
  `data: { user }` alone.
  That this is a *distinguishable* case, rather than a theoretical one, is confirmed in
  the SDK itself. `node_modules/@supabase/auth-js/dist/main/GoTrueClient.js`, `_getUser`,
  lines 2637-2648:
  ```
  catch (error) {
      if ((0, errors_1.isAuthError)(error)) {
          ...
          return this._returnResult({ data: { user: null }, error });
      }
      throw error;
  }
  ```
  A network failure reaching the auth API is raised as `AuthRetryableFetchError`, which
  `isAuthError` accepts, so it is **returned as `{ user: null, error }`** rather than
  thrown. The caller sees a null user and an error it never looks at, which is
  byte-for-byte what a genuinely signed-out visitor produces.
  The write-side consequence follows at `create-group.ts:70-76`:
  ```
  if (!user) {
    const { data, error } = await supabase.auth.signInAnonymously()
    ...
    user = data.user
  }
  ```
  and identically at `join-group.ts:38-48`. `src/lib/groups/provision.ts:49-55` then
  finds no `User` row for the new `supabaseAuthId` and creates a second person.
  For the record of what this is *not*: `src/lib/supabase/proxy-session.ts:31` also calls
  `getUser()` and also ignores the error, but that call exists only to refresh cookies and
  its failure is harmless.
- **severity** — queue
- **confidence** — certain that the error is discarded at all eleven call sites and that
  the SDK returns rather than throws on a retryable fetch failure (I read both). Likely
  rather than certain on how often a real Supabase project produces that failure in
  practice, which I could not measure without running the app against a live project.
- **How this differs from anything registered** — Pass two's F-2-3 is about the join
  form's `hasSession` *hidden field* being trusted, and names its triggers as a cleared
  cookie, an expired session, or a stale restored page. This is a different mechanism: the
  server's own `getUser()` call returning an error the server then throws away, on eleven
  paths rather than one, including every read path (which F-2-3 does not touch at all).
  Fixing F-2-3 by re-checking the session server-side does not fix this, because the
  server-side check is the thing that is lying.

### F-2-8: Onboarding asks the founder for their name, then throws the answer away if they already have an account

- **file:line** — src/lib/groups/provision.ts:49-55
- **consequence** — Step 1 of onboarding shows a required "Your name" field and will not
  let the founder continue until they fill it in. If that person already exists in the
  product, which is true of anyone who joined someone else's group first, the name they
  just typed is silently discarded and the new group is founded under whatever name they
  used the first time. So somebody who joined a friend's climbing group as "Jake" and then
  starts their own family group as "Jacob Rios" appears to every member of that new group
  as "Jake," on the roster, on every RSVP list, and on the join announcement in the feed.
  There is no way to correct it: nothing anywhere in the product edits a name. This is a
  live risk for the very first shared link, because the natural order of events for
  someone being shown the product is exactly this order: join the demo group, then try
  creating one. The field is not merely ignored, it is *insisted on* and then ignored,
  which is the part that will read as a bug rather than as a limitation.
- **evidence** — The wizard requires it, `src/app/create/Step1Describe.tsx:85`:
  `const canSubmit = founderName.trim().length > 0 && description.trim().length > 0`,
  and the action requires it again, `src/app/actions/create-group.ts:44-46`:
  `if (!founderName || !groupName) { return { error: "Something went missing..." } }`.
  It is then dropped at `src/lib/groups/provision.ts:49-55`:
  ```
  let user = await tx.user.findUnique({ where: { supabaseAuthId } })

  if (!user) {
    user = await tx.user.create({
      data: { name: founderName, supabaseAuthId },
    })
  }
  ```
  `founderName` is referenced nowhere else in the function; the existing row's `name` is
  never compared or updated. The group is then created with `founderId: user.id`
  (`:57-71`), and every surface reads the name off that `User` row.
  The parallel path in `src/lib/groups/join.ts:45-46` does the same thing, but there it is
  deliberate and documented ("submitting a name on the join form must not silently rename
  them across all groups", `join.ts:24-26`) and the join screen honestly reflects it by
  showing "Joining as Sam" instead of a name field
  (`src/app/join/[inviteToken]/JoinForm.tsx:296-302`). Onboarding has no equivalent: it
  shows the empty field to everyone.
- **severity** — queue
- **confidence** — certain about the code path. Unsure only whether the owner considers
  the carry-forward behaviour correct and the *screen* wrong, or the reverse; either way
  the two currently disagree with each other, which is the finding.
- **How this differs from anything registered** — Suppression item 6 is "a founder has no
  path to fix group details after creation," which is about the group's rhythm, venue and
  name. This is about the founder's own person-name, it is not a missing fix path but an
  answer discarded at the moment it is given, and the screen actively asks for it.

### F-2-9: Tapping Join on a dead invite link still creates a permanent account

- **file:line** — src/app/actions/join-group.ts:38-48, against src/lib/groups/join.ts:40-41
- **consequence** — The join action creates the visitor a permanent anonymous account
  first and only afterwards checks whether the invite link is real. So a stranger who
  posts a made-up link token at the join endpoint gets a real, permanent identity in the
  Supabase account store even though they join nothing and see only an error. Two costs
  follow. The small and certain one: the account store fills with identities that belong
  to nobody and are attached to nothing, which makes "how many people have used this?"
  unanswerable from the dashboard. The larger and less certain one: Supabase counts these
  toward the plan's monthly active user allowance, so an automated caller pointed at that
  endpoint spends the product's user quota rather than the product's own users spending
  it, and there is no cost cap that covers this the way the prepaid Anthropic credit
  covers model spend. The fix is free, it is running the two steps in the other order.
- **evidence** — `src/app/actions/join-group.ts:34-48` mints first:
  ```
  let { data: { user } } = await supabase.auth.getUser()

  if (!user) {
    const { data, error } = await supabase.auth.signInAnonymously()
    ...
    user = data.user
  }
  ```
  The token is only resolved afterwards, inside the transaction at
  `src/lib/groups/join.ts:40-41`:
  ```
  const group = await tx.group.findUnique({ where: { inviteToken } })
  if (!group) throw new Error("INVALID_INVITE")
  ```
  The thrown error is caught at `join-group.ts:58-64` and returned as copy. The Supabase
  auth row created at line 44 is not rolled back and nothing later deletes it. No Prisma
  `User` row is created (that happens at `join.ts:46`, after the token check), so the
  orphan lives only in the auth store, which is why this is a quota and hygiene cost
  rather than a data-model one. Note the token is never validated for shape or length
  before the query either: `join-group.ts:19` trims it and passes it through.
- **severity** — queue
- **confidence** — certain that the ordering is as described and that the auth row
  survives. Unsure how much exposure this actually carries in production: Supabase applies
  its own default rate limit to anonymous sign-ins per IP, which I could not verify against
  this project's settings without the dashboard, and that limit may already bound it to a
  nuisance.
- **How this differs from anything registered** — Build notes record a related decision at
  two places: the founder-auth entry ("Captcha on anonymous sign-in was skipped... noted as
  a production-readiness item", line 437) and the 11 Aug triage ("Captcha on anonymous
  sign-in: declined for MVP", line 1856). That decision is about deterring bots at the
  *front* of a legitimate flow, and its stated reasoning is that "the billing hard cap
  already bounds a bot's damage to downtime rather than money" — which is about Anthropic
  credit, and does not bound Supabase's user quota. This is a narrower and separate thing:
  an account created for a request that was invalid, on a path the visitor cannot possibly
  complete. Declining it is defensible on the same grounds the captcha was declined; it is
  reported because the reasoning on record does not actually cover it.

## Appendix (real, but no product consequence)

### A-2-11: The cron secret is compared with a plain `!==` rather than a constant-time comparison
- **file:line** — src/app/api/cron/orbit/route.ts:32 — `if (authHeader !== \`Bearer ${cronSecret}\`)`
- String inequality short-circuits at the first differing byte, which in principle leaks
  timing about how much of a guessed secret is correct. Against a high-entropy secret over
  a network, with Vercel's own latency jitter in the path, this is not a practical attack,
  and the endpoint offers one bit of feedback per request anyway. Recommendation: decline.
  Worth one line in a future hardening pass only if the same comparison pattern is ever
  reused for something a person types.

### A-2-12: The cron route's header comment states a fact about the repo that is no longer true
- **file:line** — src/app/api/cron/orbit/route.ts:16 ("There is no .env.example in this
  project; document in the PR"), against .env.example:22-24, which exists and already
  carries `CRON_SECRET="YOUR_RANDOM_SECRET"` with a comment
- The same stale claim is repeated in build-notes at line 632. Nothing is broken by it;
  it costs a future reader one wrong assumption about where to record a new environment
  variable. Recommendation: decline, or fold into the next touch of that file.

### A-2-13: An unvalidated client-supplied group id is passed straight into a cache API
- **file:line** — src/app/actions/rsvp.ts:73-76 —
  `const groupId = (formData.get("groupId") as string | null)?.trim() ?? ""` then
  `revalidatePath(\`/groups/${groupId}\`)`
- Unlike the `eventId` on the same action, this value is never checked against anything
  before use; the RSVP itself has already been written and validated by then. The worst a
  crafted value achieves is invalidating a cache entry for some other group's page (which
  then simply re-renders, correctly, on its next request) or naming a path that matches no
  cache entry at all. No data is read or written. Recommendation: decline.

### A-2-14: The two "you can't see this" responses are distinguishable, so a request can confirm that a given group id is real
- **file:line** — src/app/groups/[id]/page.tsx:62 (`if (!group) notFound()`) against :71
  (`if (!viewerIsMember) return <MembersOnlyWall />`); same shape at
  src/app/groups/[id]/info/page.tsx:47 / :53 and src/app/events/[id]/page.tsx:46 / :54
- An unknown id gets the branded not-found screen; a real group the caller is not in gets
  the members-only wall. The difference confirms existence. It confirms nothing else: the
  wall names no group, no member count and no rhythm, which I verified in
  `src/components/MembersOnlyWall.tsx:11-19`. Group ids are cuids and are published

  Noted only because it is a different observation from pass two's A-2-10, which is about
  the database work a rejected request still performs, not about what the two responses
  reveal.

## What came back clean (stated, because it is the point of a third pass)

- **No id-guessing hole anywhere.** I walked every entry point individually rather than
  sampling. Every write resolves the row by id and then re-derives the group from that
  row before checking membership: `gauge-vote.ts:64-84` (gauge → group → member),
  `proposal-vote.ts:67-84` (proposal → groupId → member), `proposal-answer.ts:56-70`
  (proposal → asker identity → member), `rsvp.ts` via `src/lib/events/rsvp.ts:50-59`
  (event → groupId → member, inside the transaction), `send-message.ts` via
  `src/lib/messages/create.ts:44-51` (author + groupId pair), `detect-intent.ts:66-81`
  (message → group → author identity → member), and
  `calendar.ics/route.ts:41-44` (event → groupId → member). Every group-scoped read helper
  takes `groupId` as its first argument and filters on it: `proposals/read.ts:25-26`,
  `gauges/read.ts:40-41`, `gauges/open-ask.ts:33-47`, `events/upcoming-list.ts:39` and `:56`.
- **The founder can never stop being a member**, so the founder-only actions cannot be
  reached by an outsider through a gap between the two concepts: `provision.ts:69` creates
  the membership with the group, `leave.ts:31` refuses `FOUNDER_CANNOT_LEAVE`, and
  `remove-member.ts:33` refuses `CANNOT_REMOVE_FOUNDER`.
- **No email can leave the server, because no email is stored on a person.** `User` has
  `name` and `supabaseAuthId` only (`prisma/schema.prisma:12-27`); addresses would live on
  `ContactMethod`, which no query in `src/` reads (`grep -rni "email" src/` returns four
  hits, all comments and one test). The `.ics` file writes no `ATTENDEE` line
  (`src/lib/events/ics.ts`), so the calendar path carries no person data either.
- **The invite token never reaches a client bundle it should not.** Both pages that load
  the token as part of an unfiltered `findUnique` (`groups/[id]/page.tsx:55-60` and
  `join/[inviteToken]/page.tsx:20-23`) pass only named scalars onward; the token is handed
  to a client component in exactly two places, `groups/[id]/info/page.tsx:224` and the
  onboarding share step, both of them behind a check that the viewer is a member.
  Rotation is real: `reset-invite.ts:34-35` overwrites the column with `randomUUID()`, and
  the old value survives nowhere, so every previously shared link resolves to the
  bad-invite screen.
- **No secret is inlined into the browser.** `ANTHROPIC_API_KEY` is read only at
  `src/lib/orbit/extract.ts:93` and `CRON_SECRET` only at `route.ts:28`; neither is a
  `NEXT_PUBLIC_` name, which is the only prefix Next.js inlines. `.env*` is gitignored with
  an explicit exception for the placeholder template.
- **Nothing sensitive is logged.** All eighteen `console.*` calls in `src/` log an error
  object and a static label; none logs a token, a key, a message body or a person's name.
